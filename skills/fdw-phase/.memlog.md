- (decision) Phase mechanics — open, move, close — went into the shared CLI rather than this skill's script, because they write feature state and the single-writer invariant is what keeps the registry and the folders from disagreeing. The skill keeps the judgment: proposing scope, writing exit criteria, and reporting the arc.
- (decision) phase-move physically renames the feature folder and carries everything in it. The id never changes, so a deferred feature keeps its evidence, design, client sign-off and spec. Re-creating it in the new phase would mint a new id and orphan all of that — which is the exact continuity failure requirement 3 exists to prevent.
- (decision) phase-close refuses while features are neither handed off nor explicitly deferred or dropped. Nothing should leave a phase by being forgotten. --force exists and is logged with the count it pushed past.
- (decision) Every close records blocker_count_at_handoff at the moment of closing. Reconstructed later it would be a guess, and the whole method is judged on whether that number falls across phases — so it has to be captured, not inferred.
- (decision) plan computes move-together clusters as connected components over depends_on and overlaps. Proposing a scope that splits a cluster wastes the BA's time, since phase-move would refuse it anyway.
- (event) Requirement 3 demonstrated end to end on the real store. Flagged Academy deferred while still in phase-1, closed phase-1 recording blocker_count_at_handoff 2 and the PRD path, opened phase-2 carrying 2 unresolved questions and 1 deferred feature, then moved Academy across. It arrived keeping F-001, its signal, its design folder and its spec with requirement ids F-001-R-01..R-10 intact. Store validated healthy afterwards.
- (decision) Documented the ordering at a boundary, because getting it wrong silently drops the carry-over: flag what is slipping as deferred while it is still in the closing phase, then close, then open with --from, then move. Carry-over is computed at open, so a feature moved out beforehand is invisible to it.
- (event) The eval exposed a small correctness bug in fdw-status: the digest labelled the feature count with the current phase while counting every phase, so '3 features' read as three in phase-2 when only one was. It now says '2 phases (current phase-2)' when the board spans more than one, and keeps the single-phase label when filtered. Fixed with a test.
