- (decision) Requirement ids are minted by approve, not written during drafting. The draft churns freely as the BA changes his mind — which is why the spec exists at all — and the moment it is approved the script inserts F-NNN-R-NN in order and never renumbers them afterwards. Re-approval preserves existing ids and mints only for new requirements.
- (decision) Provenance accepts two shapes: [src: anchor] for evidence from an ingested document, and [from: A2] for a behaviour that came out of the design and was signed off by the client. Both are traceable; a requirement carrying neither fails validation. The design-derived case is the common one because this method discovers requirements through the prototype.
- (decision) approve REFUSES while critical questions are open, with --accept-open-blockers as an explicit, logged override. The handoff blocker report only warns, but spec approval is the gate Vadim named as his own success criterion: ideally every blocker is closed at spec level. A gate that only warns would not move that number.
- (decision) No split command. When a spec turns out to be three features the skill says so and records the intended delivery slices, but re-slicing the registry belongs to fdw-intake, which holds the source evidence. A half-built split here would strand the design work.
- (event) Eval passed on the real store. Wrote the Academy spec from transcript-derived evidence: 10 requirements, 2 from ingested anchors and 8 from design decisions the client signed. approve refused while two critical client questions were open, accepted once they were closed, and minted F-001-R-01..R-10. The full chain resolves end to end — requirement to anchor to signal quote to the verbatim Ukrainian turn to the original file and its sha256.
- (decision) Fixed the same class of defect found in fdw-design: approve suggested a single spec-approved command the state CLI then refused, because design-approved to spec-approved skips speccing. Two fixes — scaffold now emits the command that marks the feature speccing, which is semantically right since that is when speccing starts, and approve emits the full gate-walking sequence from wherever the feature actually is.
- (note) Requirement provenance in practice skewed heavily to [from: A<n>] — 8 of 10. That is the method working as intended rather than a weakness: this approach discovers requirements through the prototype the client signed, so most requirements trace to a design decision rather than to something anyone said out loud on a call.
- (defect by user) A phase PRD was generated for the live engagement carrying eleven open questions against a standard of none. Root cause: fdw-elaborate wrote questions as prose into spec.md and nothing minted them into feature.json, the ledger every gate reads — and nothing could, because no CLI verb existed that could add a question. Eight of the eleven had existed upstream all along, invisible. Pre-flight replayed at spec-approved reported '0 critical blockers would travel into the PRD' and phase-close recorded blocker_count_at_handoff: 0, a false zero on the module's own evaluation metric.
- (decision by user) Two gates changed. (1) New 'questions' subcommand parses both question sections, stamps ids into unfiled bullets exactly as requirements get theirs, and emits the one command that files them; wrapped bullets are joined because real specs wrap, and an unparseable bullet is a named problem never a silent skip. The prose-id-not-in-ledger check is deliberately NOT bypassable by --accept-open-blockers: that flag accepts KNOWN blockers, and an id the ledger never heard of is an unknown one being hidden. That reverse check is what makes a minted id a join rather than a cache. (2) approve now refuses on ANY open question, not just critical — decisive because all eight questions in the real spec were non-critical, so a critical-only gate would have let that PRD through unchanged.

Amended requirements keep id AND position and gain a marker; nothing is deleted, because as-built.md and the phase PRD already cite those ids. ## Revision history is in SECTIONS with a non-STUB default (_No revisions yet._) so a fresh scaffold passes check with no special-casing.
