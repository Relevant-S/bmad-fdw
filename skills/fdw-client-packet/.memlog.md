- (decision) The non-negotiable — zero internal vocabulary in a client-facing document — is deterministically checkable, so the render command lints for it and refuses. Feature ids, assumption ids, t-shirt sizes, sprint/backlog/spec/FR- jargon and fdw- skill names in a document going to a paying client is the embarrassing failure this skill exists to prevent, and prose asking the model to be careful would not stop it.
- (decision) This skill writes no state of its own. The shared CLI stays the only writer: sign-off is feature-set, and answers are question-close, which was added to fdw_state.py for exactly this case — a real answer with a named source but no anchored document.
- (decision) Question ids must map answers back to features but must never appear in the client document. The mapping goes to a sidecar .map.json beside the packet, which the BA does not send.
- (note) The script cannot screenshot a code prototype. The packet describes screens in the client's language and names how to view the running prototype; screenshots the BA supplies are embedded as data URIs so the page stays self-contained.
- (event) Eval passed on the real store. Rendered the Academy packet from transcript-derived data — 2 screens, 3 assumptions rewritten as confirmable statements, 3 client questions — and verified the page contains zero occurrences of F-001, A1, unconfirmed, spec, phase-1 or Q-01. Then closed a question from client feedback and recorded sign-off; the decisions trail carries who approved, when, and via which packet.
- (event) Two defects the tests caught. The internal-id pattern carried a negative lookahead meant to avoid false positives like 'S3 bucket', which killed the true positive 'See A1 for the detail' — removed, since a false positive costs one rewrite and a false negative puts an internal id in front of a client. And the vocabulary scan was linting _comment authoring notes that are never rendered; keys starting with _ are now exempt, like ref.
- (decision) A test asserts the shipped packet.example.json passes its own vocabulary gate, so the example can never drift into demonstrating what the skill forbids.
- (decision) Headless never records sign-off. Approval is the client's act, and inferring it from an absent objection is how a project ships something nobody agreed to.
- (gap) Translating the packet exposed a hole: the vocabulary gate was English-only, so a packet written in the client's language walked straight past it. Feature ids and A/G/S references still caught, since those are language-independent, but jargon was not.
- (decision) Extended the gate to Ukrainian, including the forms this team actually says: специфікація, спека/спєка, спринт, беклог, епік, юзер-сторі, фіча, сторі-поінти, and the ASR-mangled PRD variants from the source transcript (передіжка, пірдіжка, приєртіжка). Fix hints are written in Ukrainian too, since whoever hits them is writing Ukrainian.
- (note) спека collides with the ordinary Ukrainian word for heat. Kept anyway — in a software packet it never appears, and a false positive costs one rewrite while a false negative puts jargon in front of a client.
- (decision) Fixed a silent-overwrite bug the translation surfaced: a fully Cyrillic headline slugifies to nothing, so two packets would collide on the same fallback filename and one would overwrite a document already sent. Falls back to the feature slug.
- (defect by user) Reported from a real engagement: the packet looked good but got there two wrong ways. (1) Screenshot capture leaned on whichever browser-automation MCP happened to be installed locally — the script only took --screenshot label=path.png and had no opinion on where PNGs came from, so another BA gets a different packet or none. (2) No defined way for the client to respond: the packet asks questions and nothing specifies how answers, comments or approvals come back or get recorded.
- (decision) Capture harness ships with the module: stdlib http.server over loopback (file:// resolves relative assets differently and would quietly produce a different packet) plus whatever Chromium-family browser is already on the machine, driven over CDP through a ~60-line stdlib WebSocket client. No npm, no MCP, no third-party package. Fixed optics 1280x900 @2x with captureBeyondViewport. The capture list is grounding.json's declared screens, so the capture list and the feature boundary are the same list.
- (decision by user) Response mechanism: HTML packet chosen over a Figma node, against the user's initial lean, and confirmed by them. Decisive reasons: Figma would reintroduce the exact defect being fixed in the capture half — a leg of the workflow depending on whichever MCP is installed — except on the client's side where it cannot be recovered; and a comment pinned to canvas coordinates needs an LLM judgment call to become 'this question is answered', throwing away the provenance the module is built on. Parallel commenting, Figma's real advantage, is recovered by one reply per stakeholder merged on ingest.
- (design) Round trip: reply built into the packet (agree/not-quite per assumption, answer box per question, name, one approve control), answers persisted in the client's own browser, Finish produces a copyable FDW1 block plus a plain-language summary of what they are sending. Replies travel labelled q1/a2 — no internal id ever in the client's hands, not even inside the block — and the existing .map.json sidecar becomes the join table. sync takes one reply per stakeholder from pasted block, downloaded file, or that block buried in an email; files them beside the packet for provenance; emits question-close with the client's own words as the quote.
- (rule) sync never resolves a conflict: two stakeholders answering differently leaves the question open with both answers named, because a script picking one would invent a client decision. Disagreed assumptions are corrections routed to fdw-design, not closed questions. Sign-off is withheld until every question asked has an answer, nothing is in conflict, and someone actually said yes — silence is not sign-off and one 'not yet' holds the feature. sync writes no feature state; it emits the commands.
- (fix) The reply script's join('\\n') was written into a non-raw Python triple-quoted string, so the rendered page carried a real newline inside a JS string literal — a syntax error killing the entire reply block silently, in the client's browser, where nothing upstream would notice. Made REPLY_JS raw and added an end-to-end test that drives a real headless browser: fill the form, click Finish, read the block, sync it back.
- (defect by user) gather hardcoded the prototype at design/prototype while fdw_design and fdw_capture both resolve prototype_dir from grounding.json, so any feature whose design put the prototype elsewhere was reported as having no prototype and the packet refused to build. Fixed in the source repo (a subagent had fixed only the installed copy under epp/docs/.claude/skills/). Added a regression test.
- (decision by user) Packets moved from the flat phases/<phase>/client-packets/ into phases/<phase>/features/<F-NNN-slug>/client-packets/. Asked to justify the flat folder there was no justification: gather, render and sync all take one --id and the map records one feature, so it was never multi-feature. It came from the plan's layout sketch, placed beside handoff/ by symmetry — but handoff genuinely is phase-level (it bundles every feature) and client-packets copied the shape without the property. Preserved: gather still reports packets_this_phase by glob, and sync reads the legacy phase-level folder as a fallback so a client already sent a packet still has a working reply path.
