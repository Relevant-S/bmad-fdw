# fdw Discovery State Contract v1

The shared data contract for the fdw (Feature Discovery Workflow) module. Every fdw skill reads and
writes the store through `fdw_state.py`, never by hand-editing JSON. `fdw-intake` owns this file;
`fdw_state.py init` copies it into the store as `CONTRACT.md` so the store describes itself.

## Layout

```
{discovery_folder}/            # default {output_folder}/discovery/
  CONTRACT.md                  # this file, copied at init
  registry.json                # THE INDEX — small, loaded in full, always
  decisions.md                 # mid-term memory, append-only, survives phase boundaries
  questions.md                 # derived rollup, regenerated by fdw-consistency
  glossary.md                  # canonical terms and the aliases seen in sources
  as-built.md                  # what has shipped; refreshed by fdw-handoff
  sources/
    index.json                 # every ingested source: hash, sample, features touched
    {date}-{slug}.md           # normalized source, verbatim, anchored
    .pending/                  # in-flight run scratch: source block + intake plan, cleared on apply
  phases/
    phase-1/                   # sub-phases allowed: phase-2.1
      phase.json
      features/
        F-001-{slug}/
          feature.json         # the record (registry is the index)
          signal.md            # anchored evidence — no inference
          design/              # fdw-design: prototype/, ux-notes.md, empty-state.md
          spec.md              # fdw-elaborate only — THE SANDBOX
          changes.md           # change records raised after approval
      client-packets/
      handoff/
```

## Machine files are JSON, prose files are Markdown

JSON for anything a script reads or writes: no YAML in the runtime, and YAML's implicit typing would
coerce ids, statuses, and dates in exactly the files where that is most dangerous. Markdown for
everything a human reads as prose.

## registry.json

```json
{
  "contract_version": 1,
  "current_phase": "phase-1",
  "next_feature_seq": 4,
  "phases": ["phase-1"],
  "features": [
    {
      "id": "F-003",
      "title": "Session management",
      "slug": "session-management",
      "phase": "phase-1",
      "status": "sliced",
      "flags": [],
      "size": null,
      "depends_on": [],
      "overlaps": [],
      "open_questions": {"critical": 2, "non-critical": 1},
      "updated": "2026-08-22"
    }
  ]
}
```

`next_feature_seq` only ever increases. Ids are minted once and never reused or renumbered, so a
feature keeps its id when it is deferred to a later phase — that continuity is what makes state
consistent across phases.

## feature.json

Mirrors the registry entry and adds what the index deliberately omits: `summary`, `aliases`,
`sources` (source ids that contributed), and `questions`.

```json
{
  "id": "F-003", "title": "Session management", "slug": "session-management",
  "phase": "phase-1", "status": "sliced", "flags": [], "size": null,
  "summary": "Create, schedule and populate sessions.",
  "aliases": ["sessions", "сесії"],
  "depends_on": [], "overlaps": [],
  "sources": ["2026-08-22-academy-call"],
  "questions": [
    {
      "id": "F-003-Q-01", "text": "Can sessions overlap?",
      "criticality": "critical", "owner": "client", "status": "open",
      "raised": "2026-08-22", "raised_by": "2026-08-22-academy-call"
    }
  ],
  "created": "2026-08-22", "updated": "2026-08-22"
}
```

A resolved question keeps its entry and gains `answer`, `answer_anchor`, `answer_quote`, `resolved`.
Questions are never deleted — a closed question is evidence that it was asked and answered.

## Lifecycle

`candidate → sliced → designing → client-review → design-approved → speccing → spec-approved →
handed-off → shipped`, with orthogonal flags `changed`, `deferred`, `dropped`.

Gates that hold across the module:

- Only `design-approved` may enter `speccing`. The design gate is what the client signed.
- Only `spec-approved` may enter a handoff bundle.
- At `spec-approved` and beyond the spec is **locked**: no skill edits `spec.md` in response to new
  input. A contradiction opens a change record instead. `fdw_state.py` enforces this — a
  contradiction against a locked feature fails validation unless routed as `change-record`.
- No skill advances a status it did not do the work for.

## Provenance anchors

Format: `{source_id}#{fragment}` where the fragment is `t=MM:SS` (transcript), `L=<line>` or
`L=<from>-<to>` (line-addressed document), `p=<page>` (paged document), or `s=<section-slug>`.

Every signal entry carries three fields and is rejected without all three:

- `text` — the requirement, in English, as the module understands it
- `anchor` — where it came from
- `quote` — the source's own words, **verbatim and untranslated**

A translated quote is not evidence. The source file preserves the original language; the English
lives in `text`.

## Questions

`criticality` is `critical` or `non-critical`. `owner` is `client`, `internal`, or `dev` — who has
to answer it. Ids are `{feature-id}-Q-NN`. The count in the registry mirrors open questions in
`feature.json`; `fdw_state.py validate` catches drift.

## sources/.pending/

`normalize` writes `{source_id}.source.json` here — the source block, so no skill ever transcribes a
hash — and names `{source_id}.plan.json` as where the in-flight intake plan belongs. `apply-plan`
clears both once the run lands. Anything left here is an abandoned run that can be resumed or deleted.

## sources/index.json

One entry per ingested source: `source_id`, `sha256`, `path`, `original`, `title`, `date`, `kind`,
`sample` (first ~400 chars, used for near-match detection), `supersedes`, `features_touched`,
`ingested`, and optionally `outcome: "no-new-signal"`.

A source file in `sources/` with no index entry was normalized but never ingested. That is not
corruption — it is preserved evidence from an abandoned run. `validate` reports it as
`unindexed_sources`.

## phase.json

`phase`, `status` (`open` / `closed`), `opened`, `closed`, `exit_criteria`, `features` (ids),
`carried_over`, `blocker_count_at_handoff`, `prd_path`.

`blocker_count_at_handoff` is the module's own evaluation metric — unresolved critical questions at
the moment a phase handed off. Recorded per phase so the trend across phases is real data.

## Write discipline

- Any skill that writes a feature folder updates the registry in the same run.
- `apply-plan` writes feature folders first and the registry last, so a crash leaves an index that
  under-reports rather than one pointing at folders that do not exist. `validate` names either.
- Non-obvious calls append one line to `decisions.md`.
- `questions.md` at the root is derived. Regenerate it; never hand-edit it.
